  2. Describe what renv records in a lockfile and how the project-local library works.
  3. Initialise renv in an existing RStudio Project with renv::init().

  6. Commit renv.lock (and not the library itself) to a GitHub repository.
  7. Diagnose and resolve the three most common renv issues.

What this module covers. Your R analysis depends on dozens of packages, each of which changes with every update. An analysis that runs perfectly today may produce different results — or fail outright — when a collaborator opens it on a different machine, or when you return to it six months later after updating R. renv solves this by locking a snapshot of every package version your project uses into a file you commit alongside your code. This module teaches the complete workflow from first init() to sharing a reproducible environment via GitHub.

1. Why Package Versions Matter

Before installing renv, it helps to understand concretely what problem it solves.

The “works on my machine” problem

✗ Without renv

You finish your PM2.5 analysis in January using dplyr 1.1.2. You share the code with a labmate who has dplyr 1.0.8 installed. The .by = argument to summarise() — added in 1.1.0 — causes an error they cannot explain. They spend an afternoon debugging code that is actually correct.

Or worse: the analysis runs but produces different numbers because a statistical function’s default argument changed between versions. Neither of you notices.

✓ With renv

Your project folder contains renv.lock recording the exact version of every package. Your labmate runs renv::restore() after cloning your repo. renv installs the exact versions you used — not whatever happens to be current — and the analysis runs identically.

The lockfile is a few kilobytes of plain text committed to GitHub alongside your code. It costs almost nothing to maintain.

Packages that have changed in ways that break analyses

Package Version where behaviour changed What broke
dplyr 1.1.0 .by = added; group_by() scoping tightened
ggplot2 3.4.0 size aesthetic split into linewidth + size
lubridate 1.9.0 as_date() handling of POSIXct with tz changed
vegan 2.6.0 adonis() deprecated in favour of adonis2()
lme4 1.1-30 Convergence tolerances tightened; some models now warn

⚠️ Silent version breakage is the most dangerous kind. When a breaking change causes an error, you notice immediately and fix it. When it silently shifts a default argument — a different smoothing bandwidth, a changed sort order, a reversed factor level — your results change without any indication that something is wrong. Locking package versions prevents both.

2. How renv Works

renv adds three things to your RStudio Project:

your-project/
 ├── data/
 ├── R/
 ├── your-project.Rproj
 ├── renv.lock     ← the lockfile: records every package + version
 ├── .Rprofile     ← one line that activates renv when the project opens
 └── renv/
     ├── activate.R   ← renv bootstrap script
     ├── library/      ← project-local package library (gitignored)
     └── .gitignore    ← keeps the library out of git automatically

The project-local library. Normally all your R packages live in a single shared library folder (run .libPaths() to see it). renv gives each project its own library folder inside renv/library/. Packages installed for project A do not affect project B, and vice versa.

The lockfile. renv.lock is a JSON file that records the name, version, and source (CRAN, Bioconductor, GitHub) of every package your project uses. It is small, human-readable, and the only file you need to commit to reproduce the environment elsewhere.

The cache. renv maintains a global package cache on your machine (usually in ~/.cache/R/renv/). When two projects use the same package version, renv hard-links the files rather than copying them, so you do not need gigabytes of disk space even with many projects.

📌 You commit the lockfile, not the library. The renv/library/ folder is automatically added to .gitignore by renv. Committing compiled package binaries would bloat your repository by hundreds of megabytes. The lockfile alone — typically 5–50 KB — is everything needed to recreate the library on another machine.

3. Initialising renv

Prerequisites

renv works inside an RStudio Project (.Rproj file). If your analysis is not already in a project, create one first: File → New Project → Existing Directory. See the Project Structure module for details.

Install and initialise

# Install renv once (only needs to happen once per machine)
install.packages("renv")

# Initialise renv in your current project
renv::init()

# Console output from renv::init() * Initializing project … * Discovering package dependencies … Done! * Copying packages into the cache … [33 packages] Done!

The following package(s) will be updated in the lockfile: # CRAN ——————————————————————- - dplyr [* -> 1.1.4] - ggplot2 [* -> 3.5.1] - lubridate [* -> 1.9.3] - readr [* -> 2.1.5] - tidyr [* -> 1.3.1] - vegan [* -> 2.6-6.1] … (27 more packages) * Lockfile written to ‘~/my-project/renv.lock’.

What renv::init() does:

  1. Scans all .R and .Rmd files in your project for library() and require() calls.
  2. Identifies the installed versions of every package found.
  3. Copies those packages into the project-local library (or links to the global cache).
  4. Writes renv.lock recording every version.
  5. Writes .Rprofile with one line: source("renv/activate.R").

After init(), restart R (Session → Restart R) so the new .Rprofile activates the project library.

💡 Run renv::init() early, not at the end of a project. The best time to initialise renv is right after creating the RStudio Project, before installing any packages. This way the lockfile always matches exactly what your project uses, with no orphaned packages from other work on your machine.

4. The Lockfile in Detail

renv.lock is plain JSON. Opening it in RStudio (or any text editor) shows you exactly what it records.

# renv.lock (simplified excerpt)
{
  “R”: {
    “Version”: “4.4.1”, <– R version itself is recorded
    “Repositories”: [{ “Name”: “CRAN”, “URL”: “https://cran.rstudio.com” }]
  },
  “Packages”: {
    “dplyr”: {
      “Package”: “dplyr”,
      “Version”: “1.1.4”, <– exact version pinned
      “Source”: “Repository”,
      “Repository”: “CRAN”,
      “Hash”: “fedd9d03c235d5a3ed7a05ee28588dbb” <– cryptographic hash for integrity
    },
    “ggplot2”: {
      “Package”: “ggplot2”,
      “Version”: “3.5.1”,
      “Source”: “Repository”,
      “Repository”: “CRAN”,
      “Hash”: “9e4e4760f46cd7ef851a56cb1169cbb1”
    },
     … one entry per package …
  }
}

Three fields matter most:

  • Version — the exact CRAN version pinned. renv::restore() will install this exact version.
  • Source — "Repository" for CRAN; "GitHub" for packages installed from GitHub; "Bioconductor" for Bioconductor packages.
  • Hash — a cryptographic fingerprint of the package tarball. renv uses this to verify that what it downloads is byte-for-byte identical to what you had.

Packages from GitHub

If you use a package installed via remotes::install_github(), renv records the GitHub username, repository, and the exact commit SHA — not just a version number — so the identical commit is reinstalled.

“envnames”: {
  “Package”: “envnames”,
  “Version”: “0.4.0”,
  “Source”: “GitHub”,
  “RemoteUsername”: “mastropi”,
  “RemoteRepo”: “envnames”,
  “RemoteSha”: “d7a4f3c19b2a…” <– exact commit hash
}

5. Day-to-Day Workflow

Once renv is initialised, the three functions you use regularly are:

renv::status()
Check whether the lockfile matches the project library. Run this any time you are unsure.
renv::snapshot()
Update the lockfile to reflect current installed packages. Run after installing or updating any package.
renv::restore()
Install packages from the lockfile. Run after cloning a repo or when the lockfile has changed.
renv::install()
Install a package into the project library. Equivalent to install.packages() but renv-aware.
renv::update()
Update one or all packages to their latest CRAN versions. Always snapshot afterwards.

Installing a new package

# Option A: use renv::install() directly (preferred — renv-aware)
renv::install("viridis")

# Option B: use install.packages() as normal — renv intercepts it
install.packages("viridis")

# After installing, record it in the lockfile
renv::snapshot()

# renv::snapshot() output The following package(s) will be updated in the lockfile: # CRAN ——————————————————————- - viridis [* -> 0.6.5] - viridisLite [* -> 0.4.2] * Lockfile written to ‘~/my-project/renv.lock’.

Commit renv.lock after every snapshot():

# In the RStudio Git pane, stage and commit renv.lock
# Or from the terminal:
# git add renv.lock
# git commit -m "renv: add viridis 0.6.5"

Checking status

Run renv::status() whenever you are unsure whether your library and lockfile are in sync.

renv::status()

# Three possible states * The project is already synchronized with the lockfile. # OR: packages in library not recorded in lockfile The following package(s) are installed but not recorded in the lockfile: viridis * Use renv::snapshot() to update the lockfile.

OR: packages in lockfile not installed

The following package(s) are recorded in the lockfile but not installed: viridis * Use renv::restore() to install these packages.

Updating packages deliberately

# Update a single package
renv::update("ggplot2")

# Update all packages to latest CRAN versions
renv::update()

# Always snapshot after updating so the lockfile stays current
renv::snapshot()

⚠️ Update deliberately, not accidentally. Never run update.packages() (base R) inside an renv project — it updates the system library, not the project library, and can silently break things. Always use renv::update(). Before updating, make sure your analysis still works: update on a branch, check your results, then merge and snapshot.

6. Restoring an Environment

renv::restore() is what your collaborators (or future-you) run after cloning the project. It reads renv.lock and installs the exact package versions recorded.

# Clone the repository, open the .Rproj, then:
renv::restore()

# renv::restore() output The following package(s) will be updated: # CRAN ——————————————————————- - dplyr [1.0.8 -> 1.1.4] - ggplot2 [3.3.6 -> 3.5.1] - lubridate [1.8.0 -> 1.9.3] … (31 more packages) Do you want to proceed? [y/N]: y

  • Retrieving ‘https://cran.rstudio.com/…’ … OK [downloaded 1.2 Mb] …
  • Package database updated.

renv checks the global cache first. If the required version is already cached from another project, no download is needed — restoration takes seconds. Only genuinely new versions require downloading.

The bootstrap: renv on a machine where renv is not installed

renv/activate.R is the bootstrap script. When someone opens your project for the first time, the .Rprofile runs source("renv/activate.R"), which automatically downloads and installs renv itself if it is missing, then prompts them to run renv::restore(). This means collaborators do not need to know about renv at all — opening the project is enough to trigger the setup sequence.

7. Using renv with GitHub

What to commit

Path Commit? Reason
renv.lock Yes — always This is the reproducibility record
.Rprofile Yes Activates renv when project opens
renv/activate.R Yes Bootstrap script for new machines
renv/.gitignore Yes Keeps the library out of git
renv/library/ No Auto-gitignored; too large; platform-specific
renv/staging/ No Temporary files

renv creates renv/.gitignore automatically with the correct entries. You should never need to edit it manually.

A complete GitHub workflow

# ── PERSON A: starting the project ───────────────────────────────
renv::init()
# ... do work, install packages ...
renv::snapshot()
# git add renv.lock .Rprofile renv/activate.R renv/.gitignore
# git commit -m "renv: initialise project environment"
# git push

# ── PERSON B: picking up the project ─────────────────────────────
# git clone https://github.com/marclos/RTricks.git
# Open RTricks.Rproj in RStudio
renv::restore()   # installs exact versions from renv.lock
# Ready to work — identical environment to Person A

# ── PERSON A: adding a package ───────────────────────────────────
renv::install("patchwork")
# Use patchwork in the analysis ...
renv::snapshot()
# git add renv.lock
# git commit -m "renv: add patchwork 1.3.0"
# git push

# ── PERSON B: pulling the update ─────────────────────────────────
# git pull
renv::restore()   # installs patchwork 1.3.0 to match lockfile

💡 Make renv.lock changes their own commit. Keeping lockfile updates in separate commits (e.g., “renv: add patchwork 1.3.0”) makes the package history easy to scan in the git log without wading through analysis code changes. It also makes it easy to revert a bad package update: git revert on just the lockfile commit.

.gitignore for an renv project

A minimal .gitignore for an RStudio + renv project:

# RStudio artefacts
.Rhistory
.RData
.Rproj.user/

# renv library (automatically added by renv, shown here for reference)
renv/library/
renv/staging/

# Data files too large for git (adjust as needed)
data/*.csv
data/*.xlsx

8. Troubleshooting

Problem 1: renv::restore() fails with a download error

Error: failed to download 'dplyr' [version 1.0.8]

CRAN archives older package versions, but occasionally a version is removed. Solutions:

# Option A: install from the CRAN archive directly
renv::install("dplyr@1.0.8")

# Option B: accept the current CRAN version and update the lockfile
renv::update("dplyr")
renv::snapshot()
# This changes the pinned version — test your analysis still runs correctly

Problem 2: “Out of sync” after pulling from GitHub

You pull a colleague’s changes and see the lockfile has been updated but your library has not.

# Always run after git pull if renv.lock changed
renv::status()    # confirms what is out of sync
renv::restore()   # installs the new/changed packages

A good habit: add renv::status() as the first thing you check after any git pull that includes lockfile changes.

Problem 3: Package installed but not found

You installed a package successfully but library(packagename) still says “there is no package called…”.

# Check whether it is in the project library
renv::status()

# Check which library R is looking in
.libPaths()

# If the project library is not first in .libPaths(), renv is not active
# This usually means the .Rprofile was not loaded — restart R inside the project:
# Session → Restart R

# Confirm renv is active
renv::project()   # should print your project path, not NULL

📌 renv only activates when you open the .Rproj file. If you open analysis.R directly (not via the .Rproj), the .Rprofile in the project root does not run, renv is not activated, and R uses your system library. Always open projects through the .Rproj file or via File → Open Project.

Problem 4: renv::init() in a project already tracked by git

If you have an existing git repository and add renv, git will show renv.lock, .Rprofile, and renv/activate.R as untracked files. Stage and commit them explicitly:

# From the RStudio terminal
git add renv.lock .Rprofile renv/activate.R renv/.gitignore
git commit -m "renv: add package management"

Do not run git add renv/ — that would stage the library folder before git sees the .gitignore. Stage renv/activate.R and renv/.gitignore individually.

9. Quick Reference

renv command reference

  • One-time setup: install.packages(“renv”) then renv::init()
  • After installing a package: renv::snapshot() → commit renv.lock
  • After cloning / git pull: renv::restore()
  • Are we in sync? renv::status()
  • Install a package: renv::install(“pkgname”) or renv::install(“user/repo”) for GitHub
  • Update a package: renv::update(“pkgname”) then renv::snapshot()
  • Install specific version: renv::install(“dplyr@1.1.4”)
  • What project am I in? renv::project()
  • Commit: renv.lock, .Rprofile, renv/activate.R, renv/.gitignore
  • Never commit: renv/library/

💬 Check your understanding

  1. A classmate clones your GitHub repository, opens the .Rproj, and immediately gets a prompt about renv. They have never used renv before. Walk them through exactly what commands to run and in what order to get the project working on their machine.
  2. You finish adding a new figure to your analysis, which required installing the patchwork package. List every step — including git commands — needed to share this change reproducibly with your collaborators.
  3. Why does renv commit renv/activate.R but gitignore renv/library/? What would go wrong if you committed the library instead?
  4. renv::update() updates packages in the project library. Why should you run your full analysis after updating, before committing the new renv.lock?
  5. You open an old project from two years ago. renv::restore() fails because one package version is no longer on CRAN. What are your two options, and what is the tradeoff between them?
